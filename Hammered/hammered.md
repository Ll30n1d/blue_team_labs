# Hammered — Writeup

## Информация о лабе

- **Платформа:** CyberDefenders
- **Название:** Hammered
- **Категория:** Endpoint Forensics / Log Analysis
- **Сложность:** Medium
- **Формат улик:** Архив с логами Linux-сервера (`/var/log/`)

## Сценарий

Веб-сервер-ханипот был скомпрометирован. В роли SOC-аналитика нужно восстановить картину атаки по логам, оставшимся на сервере.

## Инструменты

- `grep`, `awk`, `sort`, `uniq` — фильтрация и подсчёт
- `wc -l` — подсчёт строк в логах
- `comm` — пересечение списков

## Ход решения

### 1. Какой сервис использовали атакующие для доступа?

Смотрим `auth.log` и ищем неудачные попытки входа:

```bash
grep "Failed password" auth.log | head -5
```

Видим тысячи строк с `sshd` — значит, атака шла на SSH.

**Ответ:** `ssh`

### 2. Версия операционной системы

Смотрим `kern.log`:

```bash
grep -i "linux version" kern.log
```

Находим строку с версией ядра.

**Ответ:** `4.2.4-1ubuntu3`

### 3. Какая учётная запись скомпрометирована?

Ищем успешные входы:

```bash
grep "Accepted password" auth.log
```

Видим, что успешный вход был выполнен под пользователем `root`. Перед этим было множество неудачных попыток именно для `root` — классический брутфорс.

**Ответ:** `root`

### 4. Сколько атакующих (уникальных IP) смогли получить доступ после неудачных попыток?

Сначала извлекаем IP из неудачных и успешных попыток:

```bash
# IP с неудачными попытками
grep "Failed password" auth.log | grep -oE '([0-9]{1,3}\.){3}[0-9]{1,3}' | sort -u > failed.txt

# IP с успешным входом
grep "Accepted password" auth.log | grep -oE '([0-9]{1,3}\.){3}[0-9]{1,3}' | sort -u > accepted.txt

# Пересечение
comm -12 failed.txt accepted.txt
```

Но простое пересечение даёт слишком много IP (включая легитимных пользователей). Нужно отфильтровать по **количеству** неудачных попыток — у настоящих атакующих их сотни или тысячи.

```bash
# Считаем количество неудач для каждого IP из пересечения
for ip in $(comm -12 failed.txt accepted.txt); do
  count=$(grep "Failed password" auth.log | grep -c "$ip")
  echo "$count $ip"
done | sort -nr | head -20
```

После фильтрации остаётся **6** IP-адресов.

**Ответ:** `6`

### 5. IP атакующего, который успешно входил чаще всех

Среди шести IP из предыдущего шага считаем количество `Accepted password` для каждого:

```bash
for ip in $(comm -12 failed.txt accepted.txt); do
  count=$(grep "Accepted password" auth.log | grep -c "$ip")
  echo "$count $ip"
done | sort -nr | head -1
```

Лидер с заметным отрывом — `219.150.161.20`.

**Ответ:** `219.150.161.20`

### 6. Сколько запросов было отправлено Apache-серверу?

Смотрим `apache2/www-access.log`. Каждая строка — один запрос:

```bash
wc -l apache2/www-access.log
```

**Ответ:** `365`

### 7. Сколько правил было добавлено в фаервол?

Ищем в логах упоминания `iptables` с флагом `-A` (append — добавление правила):

```bash
grep -i "iptables" auth.log daemon.log | wc -l
```

**Ответ:** `6`

### 8. Сканирующий инструмент, скачанный на целевой системе

Смотрим `dpkg.log` — там записи об установке пакетов:

```bash
grep "install " dpkg.log | awk '{print $4}' | sort -u
```
Находим `nmap`.

**Ответ:** `nmap`

### 9. Время последнего входа с IP 219.150.161.20

В `auth.log` фильтруем `Accepted password` для этого IP и берём **последнюю** запись по времени:

```bash
grep "Accepted password" auth.log | grep "219.150.161.20" | tail -1
```

**Ответ:** `04/19/2010 05:56:05 AM`

### 10. Критичное предупреждение от базы данных

В `daemon.log` ищем сообщения от MySQL/MariaDB:

```bash
grep -i "mysql\|warning\|error" daemon.log | head -50
```

Находим предупреждение о том, что в таблице `mysql.user` есть **две учётные записи root без пароля**.

**Ответ:** `mysql.user contains 2 root accounts without password!`

### 11. Учётка, созданная 26 апреля в 04:43:15

В `auth.log` ищем `useradd` или `new user`:

```bash
grep -i "useradd\|new user" auth.log
```

Находим запись с нужной датой и временем. Имя созданного пользователя — `wind3str0y`.

**Ответ:** `wind3str0y`

### 12. User-Agent прокси, использовавшегося для сканирования

В `apache2/www-access.log` извлекаем User-Agent (поле в кавычках):

```bash
awk -F'"' '{print $6}' apache2/www-access.log | sort | uniq -c | sort -nr
```

Среди стандартных браузерных UA находим один необычный, короткий: `pxyscand/2.1`. Это прокси-сканер.

**Ответ:** `pxyscand/2.1`

## Выводы

- Атака началась с **брутфорса SSH** по учётной записи `root`.
- После успешного входа атакующие **добавили правила iptables**, **скачали nmap** для дальнейшей разведки и **создали новых пользователей** (`wind3str0y` и других).
- В базе данных обнаружены **root-аккаунты без пароля** — критичная конфигурационная ошибка.
- Один из атакующих использовал **прокси-сканер** (`pxyscand/2.1`) для веб-сканирования.

## Что потренировал

- Анализ `auth.log`: поиск брутфорса, успешных входов, созданных пользователей
- Работа с `dmesg`/`kern.log` для определения версии ОС
- Подсчёт запросов через `wc -l` в Apache-логах
- Поиск изменений фаервола в `auth.log` (`iptables`)
- Анализ `dpkg.log` для поиска установленных инструментов
- Извлечение User-Agent из веб-логов для обнаружения прокси/сканеров
- Понимание разницы между «просто IP с Accepted» и «атакующим IP» (фильтрация по количеству неудач)
- Работа с `comm` для пересечения списков
- Использование `awk` для извлечения полей из логов
